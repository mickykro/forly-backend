Watch A property's own title and its generated Facebook post copy disagree on one letter of the same neighbourhood name

איתי יעקב (Itay Yaakov), 972508505321 — Oct 7, 16:30:36 UTC, page ayty-yakb-yyavtz-vsh-ghznb

The post-preview message sent before publishing shows the property's title correctly, then its own generated ad copy misspells the same word two lines down:

🚀 הנכס מוכן לפרסום
"2 חד׳ בהמרכז השקט"

כך ייראה הפוסט:
──────────
למכירה בשכונת המרכז השכט, פתח תקווה!
דירת 2 חדרים, 51 מ"ר
...

Confirmed character-by-character (not a rendering artifact): the title uses ק (qof, U+05E7) — "השקט" is a real word ("the quiet"). The ad copy uses כ (kaf, U+05DB) — "השכט" isn't a Hebrew word at all. Both strings trace back to the same property.neighborhood field by different paths: the title via the deterministic autoTitle() template (server/page-update.js, also used in admin.js/dashboard.js), the ad copy via buildPostCopy() (server/distribution/share-kit.js), which also reads property.neighborhood directly with no further transformation. Since both read the same field through plain string templating with nothing LLM-generated in either path, the two renders should always agree — the only place in this property's life where the value itself could have been written is the one LLM call shared by two different flows: listing-extract.js's parseListing(), used both for "paste a listing to import" and for free-text page-edit requests via proposeChanges() in page-update.js. Neither call site validates an extracted proper noun (city/neighbourhood/address) against the source text it was pulled from, so a single-character transcription slip by the model — exactly the one-letter qof→kaf swap seen here — would reach a page's live field undetected, and only become visible the next time something re-derives text from it.

Not patched this cycle: it's one occurrence, the exact moment the field was written wasn't captured in anything Green API exposes (no edit-confirmation message for this chat shows the change happening), and listing-extract.js feeds two live flows — tightening its validation without a second data point risks rejecting legitimate normalizations (e.g. "ת״א" → "תל אביב") it currently handles correctly. Worth a source-text substring check on city/neighborhood/address specifically (proper nouns, which a correct extraction should never paraphrase) if this recurs.
