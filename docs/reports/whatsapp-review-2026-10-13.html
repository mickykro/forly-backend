Root cause — confirmed by running the handler directly, not just inferred: this backend's textThenPhotos() (server/whatsapp-intake.js) splits a text+photo webhook into two sub-turns — the caption alone, then the photos. Tsach's caption contains "ננקה" (an edit verb) and "תמונות", so it matches photo-choice.js's edit-request pattern on its own and resolves immediately via unansweredPhotos(), which reads chat history for an older, already-sent, unanswered photo — not the photos actually attached to this message. Because that sub-turn comes back handled:false, the code returned immediately and never ran the second sub-turn that carries the 16 (or 8) freshly-attached photos at all — they were computed, then thrown away, with nothing ever reaching n8n for them. That also explains the missing group-log entry: n8n had nothing new to log.

Fixed in this PR: when the caption alone resolves to an edit hand-off, textThenPhotos() now checks whether the triggering message also carries its own fresh photos and, if so, edits those instead of whatever the history lookup found — capped at the same 12-photo limit photo-choice.js already uses for every other edit hand-off, so this doesn't change cost exposure. Reproduced first with a standalone run of handleTurn() against a transcript shaped like this one (confirmed the bug: fresh photos discarded, stale ones substituted), then fixed and covered with a new regression test in server/whatsapp-flows.test.js (caption + fresh fileUrls, asserting the fresh photos — not an older unrelated album from history — are what gets edited). server/whatsapp-intake.test.js and server/whatsapp-flows.test.js both pass with the fix; the rest of the suite could not be run in this session (no node_modules installed here), but the two touched files (photo-choice.js, whatsapp-intake.js) have no external dependencies.

n8n — confirmed, not just inferred, plus a correction

n8n Business Handler v6 / Main Router v3 — exact node names now confirmed

Read directly from the live workflow graphs this cycle (Main Router v3, id fhyTsd1DSN6wtMGz; Business Handler v6, id lQwn7eYSuIxAZkJB) — no execution-log tool was available, so this is still a structural read, not a confirmed failed execution

Business Handler v6's lock chain: Code - Prep lock → FS - Set Lock → Code - Restore Batch → Quota - Batch Edit (HTTP to forly-intake:8787/api/quota/consume, no onError) → ... → SplitInBatches - Images → Check Stop (HTTP to forly-intake:8787/api/whatsapp/edit-cancel, no onError) → ... → eventually Forly Batch Done → FS - Clear Lock (done), or Send Stopped → FS - Clear Lock (stopped). Those are the only two nodes anywhere in the workflow that clear the lock. Quota - Batch Edit and Check Stop are the only two calls to the internal gateway with no error branch — a failure or timeout on either halts the whole execution before either Clear Lock node is ever reached.

Main Router v3's "hold on" fallback (Switch - Route "locked" → ... → IF - Should Send Lock Reply? → GreenAPI - Send Lock Reply, HTTP to forly-intake:8787/api/whatsapp/send) depends on the same internal gateway, also with no error branch — so if that gateway call fails, the fallback silently fails too, exactly matching why none of Nofar's ~30 follow-ups got even a "hold on" reply.

Correction to the "permanent lock" framing: Main Router v3's own Code - Resolve Route node computes a stale-guard (maxMs = total × 95000 + 120000) and forces locked = false once that's elapsed, regardless of the Firestore document's own active flag — so the Firestore lock document itself leaks (stays active:true forever), but it stops gating routing after a few minutes. This means the 39-hour silence needs a second explanation beyond "stuck lock" — most likely that every retry re-enters the same chain and hits the same unguarded gateway call again. No execution-log tool is available via the n8n MCP tools in this session to confirm that directly (only get_execution by known execution id — there's no way to list or search past runs by date or phone).

Recommended fix (unchanged from yesterday, now with exact node names): add onError/continueOnFail to Quota - Batch Edit, Check Stop, and GreenAPI - Send Lock Reply, each routing failure to its own cleanup/Clear-Lock path; separately, a scheduled sweep that clears any Firestore lock older than a few minutes so a future failure self-heals instead of leaking indefinitely.
