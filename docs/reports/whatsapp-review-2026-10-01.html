This time the system did recognize the correction and asked for confirmation — but the agent's natural reply, the number and the button's own word together ("1.כן", matching the numbered option "1 · כן" the bot itself had just sent), fell through. Two independent checks each expect only an exact form: server/whatsapp-intake.js's numbered-reply resolver matched just a bare digit with optional trailing punctuation and nothing else, and property-draft.js's command parser looks up the cleaned text as a whole word. Neither matched "1.כן", so cmd stayed unset — and the handler for a pending confirmation unconditionally clears draft.pending_changes before checking whether the reply was actually yes or no (server/whatsapp-intake.js:309-318), so the change was thrown away with no error and no re-ask. The agent gave up and said "build the page" as-is; the draft had since drifted into a stale-draft resume prompt, which re-surfaced the original fields — so the page that went live still reads ₪285,000 for what the agent named three times as a €285,000 property in Crete, the same roughly-4× undervaluation from yesterday's report, just reached through a different gap.

Fix: a numbered reply is now read as the button it maps to when the text after the number is empty or is exactly that button's own word — "1", "1.", and "1.כן" (when option 1 is "כן") all resolve the same way. A number followed by anything else ("1 תודה") still falls through unchanged, so this doesn't widen what counts as a confirmation.

A regression test replays this exact exchange (propose a price change, confirm with "1.כן", and a control case where unrelated trailing text must not be read as a confirmation) in server/whatsapp-intake.test.js. The standalone currency-correction phrasing from the first exchange above ("אני רוצה שתכתוב … € … אתה יכול?") is a second, smaller gap — a polite request rather than a direct statement — left open below rather than folded into this fix, since it needs its own recognizer, not a reply-parsing change.
