Bottom line

One real bug this cycle, reproduced end-to-end with a clean root cause, fixed in code: at 08:56 UTC on Oct 8, 972508505321 (איתי יעקב) replied — by quoting WhatsApp's own "your page is live!" message — asking to fix a one-letter typo in the page's title ("במרכז השכט" instead of "השקט"). The bot didn't recognize this as an edit request at all: an old, empty (0-photo) draft had gone stale and silently "caught" the message instead, so the agent was walked through the entire new-listing intake a second time — city, price, rooms (misunderstood once), size, floor, neighbourhood, description, 8 photos, template choice, a fresh video — and ended up with a second, duplicate live page, rather than a one-line fix to the first. Root cause: server/property-intent.js's word gate never considered the word "title" (כותרת) property-related, so the message never reached the intent classifier; and even had it, server/whatsapp-intake.js's "paused draft" branch never checked for an update intent before resuming the stale draft. Both are fixed this cycle (see below), with a regression test reproducing this exact transcript.

The typo itself is now corroborated from a second, independent source: yesterday's report flagged a one-letter mismatch between this same page's title and its generated Facebook ad copy as a single, unpatched data point. Today, the WhatsApp link-preview metadata embedded in the agent's own quoted reply shows the same misspelling ("השכט") in what renders as the page's title. That's still the same lineage (one agent, one property), not an independent second customer, so — per the standing practice of not changing a shared extraction path on one data point — listing-extract.js itself is not touched this cycle; it stays on the watch list below.

One business decision is left for the operator, flagged by WhatsApp rather than decided here: the agent now has two live pages for the same Petach Tikva listing (the original, with the typo, and the duplicate built this cycle, spelled correctly). Cleaning that up — archiving one, contacting the agent, or something else — is a product/support call, not this review's to make. No n8n change is needed this cycle: the standing n8n items (photo-batch progress spam, the competing-handler race, the away-message guard fix recommended 2026-10-07) all got zero new evidence this cycle and are carried forward unchanged, per standing practice against re-notifying with nothing new to report.

Fixed this cycle

Fixed A correction naming an already-live page was swallowed by a stale, unrelated draft

972508505321 (איתי יעקב) — Oct 8, 08:56–09:57 UTC

The agent quote-replied to the bot's own "🎉 דף הנכס שלך באוויר!" message:

שלום, רשום בכותרת המרכז השכט ולא השקט כפי שצריך להיות רשום.
תתקן לי בבקשה במהירות
יש לך טיוטה פתוחה: 0 תמונות.
להמשיך אותה, להתחיל נכס חדש, או לבטל?
1 · המשך · 2 · חדש · 3 · ביטול

The agent answered "1" (continue) and was walked through the full intake again — city, price, "2 חדרים" (after one misunderstood retry on rooms), size, floor, neighbourhood, a free-text description, 8 photos, and a template choice — ending in a brand-new page (…vsh-8as2p) at 09:57 UTC, distinct from the original (…vsh-ghznb, built Oct 7 16:30). The typo was never corrected on the original page; a second, duplicate page was built instead. Besides the wasted back-and-forth, this cost a full re-run of photo processing, template selection and video generation — exactly the kind of "unnecessary generation" this review is meant to catch.

Two independent gaps let this happen, both in this repo:

  • server/property-intent.js's PROPERTY_WORDS gate (which decides whether a message is even worth an LLM intent check) didn't include "כותרת" (title) or any correction wording, so a message about a page's title — with no "נכס"/"דירה"/"דף" in it — never reached the classifier.
  • server/whatsapp-intake.js's "paused draft" branch (an old draft idle past PAUSE_MS) unconditionally treated the next message as an answer to "continue / new / cancel?", without ever checking — as the live, non-paused "active" branch already does a few lines up — whether the message is actually an update request for a different, already-built page.

Fix: added "כותרת" to the word gate, and added the same openerOf → updatePage check to the paused-draft branch that the active-draft branch already has. With both in place, this exact message now matches the live page by its own words ("המרכז", "השכט" both appear in it) and replies with a direct edit link instead of restarting intake. A regression test in server/whatsapp-intake.test.js reproduces the transcript above end-to-end.

General improvements / commonly-requested gaps

Addressed this cycle "Fix my page" requests that don't say "page"

The one unmet request surfaced this cycle — an explicit, polite, well-formed correction asking to fix a typo quickly — is exactly the bug fixed above. It's the clearest "prevent unnecessary generation" finding available from this sample: a one-field correction turned into a full re-intake, a second video render, and a duplicate page, purely because the routing never got a chance to recognize the request.

Worth considering, not acted on The quoted-reply's own link is discarded before it reaches this backend

The agent's reply carried a WhatsApp quotedMessage/stanzaId pointing at the exact prior bot message (and so, indirectly, the exact page) — richer than the free-text word-matching matchPage() in server/page-update.js has to fall back on today. Whether that structured context reaches this backend's /intake endpoint at all depends on what n8n extracts from the webhook before calling it; this review didn't trace that path today, since the word-matching fallback already resolves this specific case once the gate fix (above) lets it through. Worth a look if a future case has no page text in common with the message at all.
